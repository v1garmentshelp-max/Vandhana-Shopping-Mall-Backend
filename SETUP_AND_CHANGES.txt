V1GARMENTS — ORDER OPERATIONS UPDATE 1.6
Prepared: 03 October 2026

Updated backend, website, mobile source, Android test APK, admin integration
files and a standalone order-admin application are included.

WHAT WAS FIXED AND ADDED

1. Cancellation visibility
   Customer requests appear immediately in the admin queue and older
   /api/orders and /api/sales/admin lists, before cancellation is completed.
   Display status, reason, request time, payment method, refund amount and
   points are available. Dispatch pauses while an active request is checked.
   Staff can verify/process a cancellation or reject it with a recorded reason.

2. Refund tracking and duplicate protection
   Online refunds use the original captured Razorpay payment. The backend
   checks the payment, currency, order and exact approved amount in paise.
   One durable refund operation and immutable idempotency key are saved before
   contacting the gateway. Timeout retries reuse the same key and body.
   Pending, processed, failed and review-required states, provider reference
   and timestamps are visible. Signed refund webhooks fetch the authoritative
   provider result; repeated events cannot finalize a refund twice.
   Failed refunds require reconciliation before any replacement is considered.
   COD refunds require a completed bank/UPI transfer reference and exact amount;
   recording that reference does not send money.

3. Points, stock and invoice consistency
   Confirmed cancellations restore eligible stock and redeemed points once.
   Partial returns allocate cash/points across the original invoice quantities.
   Restoration preserves the original reward lot expiry; expired points do
   not become new, unexpired points. Delivery and COD charges remain excluded
   under the existing product-only refund policy. Older orders with missing
   fee or item evidence are held for review instead of guessing an amount.

4. Returns and reverse shipping
   Shiprocket return orders now use the customer's address as pickup and the
   original branch warehouse as destination, with original invoice prices.
   Booking IDs are saved before return courier/AWB/pickup actions. A timed-out
   booking can be linked using its existing RET-{return_id} reference.
   Staff can inspect received goods, record notes and explicitly choose whether
   sellable stock should be restored. Receipt, restock and refund are separate
   actions. A courier delivery webhook alone cannot restock goods or refund.
   Customers can see reverse shipment status and AWB on website/mobile.

5. Admin operations and audit
   Search, pagination, payment/status filters, cancellation/return/refund queues,
   summary counts and RTO/shipping exceptions are available. Order details show
   items, totals, carrier data, refund operations, rewards and a database audit
   timeline. Visible screens refresh every 30 seconds and support manual refresh.
   Branch admins are scoped to their branch; super admins can review all branches.
   Existing branch-role names are supported when the token has a branch_id.

6. Shipping reliability
   Existing/uncertain forward bookings must be reconciled before creating a
   replacement. AWB and pickup attempts retain recoverable state. Measured
   parcel values are accepted for manual dispatch and return approval.
   Carrier status uses the current event rather than old history/estimated dates.
   Indian carrier timestamps are interpreted correctly; older events cannot
   overwrite newer tracking. RTO and failed/out-for-delivery events are not
   treated as delivered. Labels, invoices and manifests are available to staff.

7. Website and mobile parity
   Both show cancellation, refund references, points, returns and order history.
   Mobile checkout now requests policy version 2 with the selected payment
   method, matching website delivery/COD charges. Payment recovery is disabled
   for cancelled/cancellation-pending/refunded orders. Native version is 1.6.0,
   Android versionCode 7 and iOS buildNumber 7.

8. Additional ownership protection
   Legacy cart, wishlist and profile APIs now require the owning customer session;
   the website callers include authentication. Legacy sales reads enforce customer
   ownership or staff/branch scope. The older manual B2B creation/status endpoints
   now require super-admin access. This is an access change for any external
   client still calling those legacy endpoints without authentication.

BACKEND SETUP

Use Node.js 24 and the existing PostgreSQL database/schema.
From vandhana-backend:

    npm ci
    npm run migrate:mobile
    npm run migrate:commerce
    npm run preflight:mobile
    npm run preflight:commerce
    npm start

The mobile migration prepares the earlier supplied mobile/shipping schema and
is repeatable. The commerce command applies 20260929_store_commerce.sql and
20261003_order_operations.sql transactionally. The new migration adds schema
and audit triggers; it does not rewrite customer balances or original order totals.
Older installations must satisfy the base schema preflight before migration.
If it fails, preserve the error and resolve the schema difference before deploying.

Set the server values in .env.example using your existing real credentials:

    DATABASE_URL, DB_SCHEMA, JWT_SECRET
    RAZORPAY_KEY_ID, RAZORPAY_KEY_SECRET
    MOBILE_RAZORPAY_WEBHOOK_SECRET or RAZORPAY_WEBHOOK_SECRET
    SHIPROCKET_API_USER_EMAIL, SHIPROCKET_API_USER_PASSWORD
    SHIPROCKET_WEBHOOK_TOKEN
    MOBILE_BRANCH_ID and CORS_ORIGINS

Keep the existing real JWT secret when applying the update. Default development
secrets are refused by the new protected routes. All provider secrets stay on
the backend. Never put a gateway secret or Shiprocket password in web/mobile env.
Retain your existing SMTP, Cloudinary and other application environment values.

Configure SHIPROCKET_DEFAULT_WEIGHT_KG, SHIPROCKET_DEFAULT_LENGTH_CM,
SHIPROCKET_DEFAULT_BREADTH_CM and SHIPROCKET_DEFAULT_HEIGHT_CM for automatic
forward bookings. If absent, legacy defaults are 0.5 kg and 10 x 10 x 5 cm.
Those values must match your packed parcels. Manual staff booking accepts actual
measurements; it does not change an already-created carrier booking's dimensions.

SHIPROCKET CONFIGURATION

Create/use a Shiprocket API user in your own account. Map an existing pickup
location to each fulfilling branch. Include complete warehouse address, city,
state, pincode and real warehouse phone; returns cannot be approved without
valid customer and destination details.

Webhook URL:
    https://YOUR-BACKEND/api/webhooks/orders
Authentication header:
    x-api-key: the exact SHIPROCKET_WEBHOOK_TOKEN value configured on the backend

Use /api/webhooks/orders for the provider callback. Carrier webhooks update
shipment tracking and order audit; reverse-shipment events do not mark goods
received or authorize stock/refund actions.

RAZORPAY CONFIGURATION

Choose ONE callback URL for the shared website/mobile backend:
    https://YOUR-BACKEND/api/mobile/payments/webhook
or the alias:
    https://YOUR-BACKEND/api/storefront/payments/webhook

Enable payment.captured, refund.created, refund.processed and refund.failed.
Use the same webhook secret in the Razorpay dashboard and backend. The body must
reach the raw-body route unchanged so its HMAC signature can be verified.
Do not register both aliases for the same events merely because both exist.

POLICY PRESERVED / CHECKOUT PARITY

The existing store policy remains: cancellation within 7 days before dispatch,
returns within 7 days of confirmed delivery, innerwear excluded, product-only
refunds, delivery/COD fees excluded. Changing these business rules is a separate
policy decision and should update customer-facing copy and backend rules together.

New version-2 checkouts use the product subtotal before rewards for the threshold:
  Below Rs 1000: delivery Rs 30; COD adds Rs 10; online adds no COD fee.
  Rs 1000 or above: delivery Rs 0; COD adds Rs 30; online adds no COD fee.
Server STORE_* environment values can override these defaults. Existing saved
legacy checkouts keep their original invoice; they are not repriced on recovery.
Refunding all products can still result in PARTIALLY_REFUNDED because fees remain
excluded. Points and cash are tracked separately.

PROVIDER / DATABASE ACCEPTANCE BEFORE CUSTOMER RELEASE

The automated tests used isolated database fixtures and simulated provider APIs.
They do not prove your live database, credentials, carrier account or signing
configuration is deployed correctly. Verify with your own staging/provider setup:

  - COD and captured online orders, with and without reward redemption.
  - Customer cancellation visible immediately to the correct admin branch.
  - Duplicate cancellation processing restores stock/points only once.
  - Provider pending/processed/failed refund and repeated signed webhooks.
  - Refund after a timeout recovers the same provider request, without a new key.
  - Partial return pickup/AWB, receipt inspection, optional stock restoration
    and exact cash/points allocation across multiple selected quantities.
  - Another customer/branch cannot read or change the order.
  - Delivered/RTO/out-for-delivery carrier events and stale events.
  - Android native login, checkout, payment, cancellation and return screens.
  - Existing admin navigation and other modules after the complete admin merge.

REMAINING OPERATIONAL LIMITS

receipt/refund or NDR rescheduling engine was not added. Verify returned goods
at the warehouse before deciding stock/refund treatment. Replacement-order
fulfillment remains your existing workflow; this update covers return/refund
inspection and shipping rather than creating a new exchange checkout.

Older ambiguous invoices/provider bookings require staff reconciliation.
